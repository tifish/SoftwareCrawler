## 1. 要解决的问题

装机、重装和内网离线分发需要常备一批 Windows 软件的**最新安装包**（当前配方约 113 项：输入法、浏览器、IM、IDE、显卡驱动、CUDA、运行时、JDK/Python、CLI 工具等）。手工维护有四个绕不开的麻烦：

1. **官网很少给稳定直链**，下载入口藏在若干次点击或一段页面脚本之后，链接本身还带版本号、按会话生成。
2. **新版本没有通知**，只能定期人肉巡检；巡检一次的成本随软件数量线性增长。
3. **部分站点对自动化浏览器有额外拦截**（人机挑战、下载保护），而同样的地址用普通 HTTP 客户端却能直接取到。
4. **结果要落在确定的目录结构里**，供离线装机脚本直接消费，且不能出现"下了一半的文件"。

**目标**：把"怎么从官网页面走到下载链接"一次性写成配方，之后由程序自动按时间表重跑；**只在有新版本时才替换本地文件**，没变就什么都不做。

## 2. 用户与使用场景

- **配方维护者（交互式）**：在表格里增删软件、编写和调试点击序列/脚本、单项测试、看失败原因。这是日常工作量的大头，所以"写配方—测一项—看它为什么慢/为什么失败"这条回路必须短。
- **常驻（默认形态）**：程序随登录启动、隐藏在通知区域，自己按时间表跑全量、按短间隔跑高频检查。这条路径**不能有任何需要人点的东西**，也不能抢焦点、不能弹窗口——它全天都在用户的机器上运行。
- **无人值守（一次性）**：`SoftwareCrawler.exe --download-all --auto-close`，跑完就退。保留给手工触发和外部调度，不再是默认的定时方式。
- **离线消费者**：拿着下载目录去装机的人或脚本。目录里出现的文件必须都是完整可用的。
- **AI agent**：本仓库把 agent 当作一等使用者，要求功能在运行时可被程序化验证（见 §4.7）。

## 3. 范围

**做**：按配方抓取下载链接、下载、判重、可选解压、可选执行钩子脚本、批量与定时、配方与本机设置的分离存储、运行时自检与调试接口、自更新。

**明确不做**（这些是边界，不是"还没做"）：

- **不是包管理器**：不安装、不卸载、不解析依赖、不管理已装版本。程序的产出物就是磁盘上的安装包。
- **不做并发下载**：全局只有一个浏览器会话，下载严格串行。想提速要从"每一项等多久"入手，不是从并发入手。
- **不猜用户意图**：旧版本清理只按配方里显式给出的文件名模式执行，程序不去推断"哪些文件属于这一项"。
- **不做站点专用硬编码**：站点差异一律通过配方字段表达；只有当一类差异反复出现且无法用现有字段表达时，才考虑加一个新字段。
- **不跨平台**：Windows 专用（WebView2 + WinForms）。
- **不做配置云同步**：配置存放位置可切换到用户自己的同步目录，同步本身交给用户的工具。

## 4. 功能需求

每条给出**要求**、**为什么**、**怎么算满足**。

### 4.1 配方：一个软件怎么下

- **要求**：一个软件 = 一行配方，描述"从哪个页面出发、按什么顺序点/执行什么脚本、在哪个 iframe 里、等多久、下完怎么处理"。配方最多支持 5 个顺序步骤，最后一步应触发下载。
- **为什么**：绝大多数站点的差异是"点击路径不同"，把它数据化才能让新增一个软件是"填一行"而不是"写一段代码"。
- **怎么算满足**：新增一个常见软件不需要改任何 C# 代码；配方文件是人可读、可 diff、可提交的单行制表符记录。

补充要求：

- **配方与本机选择必须分家**。"这个软件怎么下"是所有用户共享的知识（进版本库）；"我这台机器要不要下、下到哪、走不走代理"只属于本机（不进版本库）。两者按软件名关联，增删行、排序都不能让本机设置错位。
- **必须能绕开浏览器**：部分站点对自动化浏览器发人机挑战、对普通 HTTP 客户端放行，配方要能声明"直接用 HTTP 客户端取这个地址"。
- **脚本编辑要能用外部编辑器**：多步脚本合成一个临时 `.js` 交给用户配置的编辑器，保存后拆回各步。编辑器的换行风格不得改写配方内容。

### 4.2 抓取与下载

- **要求**：按配方逐步等待页面就绪、滚动到目标、点击或执行脚本，拦截浏览器发起的下载并把文件落到指定位置；全程可取消。
- **为什么**：页面就绪的判定是这个程序最主要的技术风险来源——判早了点在半成品页面上（表现为"点了没反应"，白等满超时再整项重试），判晚了每一项都交固定过路费（113 项乘起来就是几十分钟）。
- **怎么算满足**：
  - 就绪判定基于页面自身的信号合成，**不使用固定 sleep 作为主要手段**；配方里的等待秒数是下限而非每项必交的成本。
  - 一次点击失败要能区分三种原因：页面还没就绪 / 元素定位不对 / 元素在但点了无效。诊断信息必须能把这三者分开（见 §4.7）。
  - 冷缓存（夜间无人值守的常态）下的表现才是验收标准，不看二次运行的缓存命中结果。
- **可选代理**：代理是本机设置，是否使用由每个配方项自己决定（默认不用）。切换代理不得要求重启程序。

### 4.3 更新判定：幂等是硬要求

- **要求**：同一个配方跑一百次，只要远端没有新版本，磁盘上就不应发生任何变化，也不应产生新的网络下载。
- **为什么**：全量定期跑一遍是常态用法。如果判重不可靠，要么每次重下几十 GB，要么漏掉真正的更新。
- **怎么算满足**：
  - 在**开始传输文件体之前**就能判定"要不要下"，依据来自响应头（大小、最后修改时间）与本地已有文件/已记录的元数据。
  - 判定必须对两种下载方式（浏览器拦截、直接 HTTP）用同一套规则。
  - 解压后归档被删除的项，仍然要能判定更新——不能因为"本地找不到那个 zip 了"就重复下载。
  - 文件名带版本号、每次都变的站点也要能判重（靠配方给出的文件名模式定位旧文件）。
  - 存在"只查不下"的模式：走完整条链路直到能回答"有没有更新"，然后取消传输。这是交互式测试和自动化验证的默认方式。

### 4.4 下载后处理

- **要求**：可选解压（保留压缩包内目录结构，或按配方要求展平到根目录）；可选在下载后/解压后执行目标目录里的钩子脚本；可选把同一份结果投递到第二个目录。
- **为什么**：一部分"软件"其实是绿色包或裸二进制，装机侧需要的是解开后的目录，或者需要一段本地安装脚本把它摆到正确位置（`bin/InstallScripts/` 就是这类离线安装脚本的母本）。
- **怎么算满足**：
  - 解压和钩子失败 = 该项失败，且**不重试**——文件已经在盘上，重下没有意义；失败要停在能看出是哪一步的状态上。
  - 归档只有在本次**实际成功执行**了解压或钩子之后才删除；脚本文件仅仅存在不构成删除条件。
  - 解压前可按配方模式清理目标目录顶层的旧文件，否则带版本号的抽出物会新旧并存。

### 4.5 批量、定时与无人值守

- **要求**：一键跑全部（或选中项）；单项失败不影响后续项；可随时取消并落到当前项上；命令行可以"跑完就退"。
- **为什么**：无人值守的那趟要能自己跑完自己收尾；白天维护配方时要能随时叫停。
- **怎么算满足**：
  - 取消无论由菜单、快捷键还是调试接口发起，都作用在同一批任务上。
  - 只有**可能是瞬时故障**的错误才重试（点击失败、脚本失败、超时、HTTP 非 2xx、字节数不足）；配置性错误（目录建不出来、文件名非法、复制失败）一次就判死，不浪费重试预算。
  - 同一个程序目录同时只允许一个实例；被挡下时，交互式启动要把已有窗口提到前台，无人值守启动要**安静退出**。

**定时由程序自己管，不交给系统计划任务**：

- **要求**：两套时间表并存。**全量**在用户配置的若干个时刻跑所有启用项；**高频检查**按一个短间隔（默认 10 分钟）只跑显式打开了开关的那几项。两者共用同一个批次和同一个浏览器会话。
- **为什么**：常驻实例常年持有单实例锁，外部计划任务起的第二个副本只会被挡下并安静退出——定时和常驻二选一，不能都要。而 113 项全量一趟是几十分钟量级，本身就不可能按 10 分钟的节奏跑，高频那一档必须是用户点名的一小撮。
- **怎么算满足**：
  - 关掉窗口不等于退出程序；时间表在通知区域里继续走。
  - 改时间表和间隔不需要重启，下一次判定就用新值。
  - 错过的时刻只补跑一次。关机一整个周末再开机，是补一趟，不是把错过的每个时刻都重放一遍。
  - 记住上次全量跑完的时刻并跨重启保留，否则每次重启都会重爬一遍。
  - 首次启动不立刻跑全量。

**不打扰是这条路径的硬要求**（它全天都在用户机器上）：

- 后台轮次开跑前要先判断现在是不是好时机，两种轮次条件相同：已有批次在跑、Windows 报告用户忙（全屏、投影、勿扰）——任一成立都不开跑。
- **主窗口开着不是限制条件**。它曾经是，结果高频只在没人看的时候运行，用户无从确认它有没有在工作——一个观察不到的功能等于不存在。代价是开着窗口干活时到点的全量照跑，要拦就手动取消。
- **遇到坏时机就直接丢掉，两种轮次都一样**，不排队、不补跑：到期即算用掉，下一个时刻才是下一次机会。一趟迟到的下载比不下载更糟——它会在用户毫无预期的时候抢走浏览器。
- **一个被挡下的全量不能顺带卡住高频**。两者是否到期必须各判各的——曾经共用一条判定路径，结果全量等了四个小时，高频四个小时没跑。
- 后台运行时不抢焦点、不进任务栏、不弹任何对话框，浏览器窗口也不能出现在用户眼前。
- 同一个原因反复挡住时只记一条日志——一天 100 多轮，重复日志会把有用信息淹掉。

### 4.6 配置、多机与多 worktree

- **要求**：用户的数据和仓库里的模板共存，**任何一方都不会被悄悄覆盖**。
- **为什么**：这是本工程历史故障最集中的地方。配方随程序升级刷新，而用户的启用状态、下载目录是不可再生的本机数据（没有版本库可回滚）。
- **怎么算满足**：
  - 升级只刷新模板，不动用户已在用的清单。
  - 程序在自己写文件之前，必须能判断文件是否**在程序之外**被改过；被改过就走合并，宁可放弃本次保存，也不吞掉用户在编辑器里的修改。
  - 清单里暂时没有、本机设置里却有的条目要保留（清单变短往往是临时状态），清理它们必须是用户的显式动作。
  - 写入是原子的，并且每天保留一份改动前的原始内容，备份放在程序目录之外。
  - 存放位置可在"随用户（AppData）/ 便携（程序目录旁）/ 自定义"之间切换；**程序目录旁存在配置目录时强制便携**——这一条同时保证了多个 worktree 各自独立、互不干扰。

### 4.7 可观测性与可自动化

- **要求**：程序运行期间，外部（人或 AI agent）能读写内部状态、查看控件树、截图、跑单项抓取、查页面就绪诊断、查配置监视状态、查定时状态。
- **为什么**：这个程序的失败几乎都是"在真实页面上、在真实时序下"才出现的，读代码和读日志定位不了。可编程的运行时接口是主要调试手段，也是 agent 验证自己改动的唯一途径。
- **怎么算满足**：
  - 通道只在 Debug 构建监听，且一个副本只可能连到它自己目录的那个实例。
  - 传输不占用网络端口（不弹防火墙、不需要分配端口）。
  - 程序没启动时，通道要能软失败而不是让客户端把它标成不可用；程序重启后无需重开会话。
  - **新增功能时，必须把可供验证的入口一并加进这套工具**（仓库既定规则，见 AGENTS.md）。

### 4.8 分发、安装与自更新

- **要求**：一条命令完成安装；缺少 .NET 桌面运行时时自动补齐；**安装过程不写注册表**；卸载 = 删目录。程序能自己检查并应用更新，Debug 构建不更新。
- **为什么**：这是个工具类程序，安装要足够轻，能被随手部署到任何一台待装机的机器上。
- **怎么算满足**：安装后卸载不留残留；更新过程中程序自己退得干净、换完文件能自己起回来。
- **注册表的唯一例外**：开机启动写 `HKCU\...\Run` 下的一个值，且只在用户显式打开这个开关时才写、关掉就删。除此之外程序不碰注册表。卸载时若开着这个开关，需要连它一起删——这一条要写在 README 的卸载说明里。

## 5. 用户可见的行为契约

这些是对外承诺，改动时优先保住。每一条都对应过一次真实故障。

1. **目标目录里只会出现完整文件。** 在途文件永远不写进目标目录——目标目录可能是 UNC 共享，也可能正被同步工具监视，不完整的文件会被同步出去。这个取舍试过一次并撤回了。
2. **没有更新就不动磁盘。** 不重下、不重写、不刷新时间戳。
3. **不覆盖用户在程序之外做的修改。** 冲突时合并，合并不了就放弃本次保存并留下痕迹。
4. **本机设置只有一份、没有版本控制。** 任何会重写它的改动都要先想清楚失败时怎么恢复；测试涉及它时先备份。
5. **配方文件里不出现"这台机器的选择"。** 否则会污染所有用户的版本库。
6. **无人值守路径上不弹任何需要人点的东西**，也不抢焦点。常驻实例全天在用户机器上跑，一个对话框会把整条时间表挂在那里。
7. **关掉主窗口不等于退出程序。** 常驻形态下那是收进通知区域；退出是通知区域菜单里的显式动作。
8. **点错链接下到 HTML 要判失败**，而不是把一个网页存成安装包——文件类型白名单是这条的兜底。
9. **旧版本清理只按显式模式，且有数量上限**。模式一次匹配到过多文件时整体放弃并告警，挡住"把模式指向通用下载目录"这类事故。
10. **同一程序目录只跑一个实例。** 两个实例共用同一份浏览器 profile 会让需要代理的条目整批失败。

## 6. 非功能需求

- **平台**：Windows，.NET 10 桌面运行时，非自包含发布。
- **性能**：以"113 项冷缓存全量跑一遍"为基准衡量。优化的对象是每项的等待时长，不是并发度。任何提速方案都必须先证明它不会让已知的慢站点（页面脚本装配晚的那几类）回退到"点了没反应、白等满超时"。
- **健壮性**：网络抖动、站点改版、浏览器进程异常都属于预期内的事；单项失败必须被隔离在这一项内。
- **安全与侵入性**：不开网络端口、不要求管理员权限（补装运行时那一步除外）；注册表只碰 `HKCU\...\Run` 下开机启动那一个值，且要用户显式开启。
- **可移植/可并行开发**：同一台机器上多个 worktree 各自独立运行、互不干扰配置与调试通道。
- **可测试性**：不依赖 UI 的逻辑（配置文件格式、设置合并、批量顺序与取消、旧版本清理判定）必须能在 xunit 里验证。

## 7. 既定取舍：不要重开的口子

这些方案被认真试过并撤回，重开它们等于重现一次已知故障。细节与实测数据见 [Architecture.md](Architecture.md)。

| 想法 | 为什么撤回 |
| --- | --- |
| 直接下载到目标目录，省一次跨卷复制 | 目标目录性质不确定（UNC / 被同步监视），"只有完整文件才出现"这条更值钱 |
| 先判 href 是不是真地址、再判可见性 | 有站点的真链接一开始就在 DOM 里但隐藏着，点它毫无反应；**隐藏通常说明页面还没装配好** |
| 检测元素"绑没绑点击处理器"来省掉等待 | "绑没绑"看得见，"能不能用"看不见；有站点处理器早就绑上了，它依赖的下载地址还没取回来 |
| 用第一次网络静默上报作为计时锚点 | 静默会上报多次，第一次常落在加载早期的空档里，会让脚本跑在半成品页面上 |
| 按行号关联配方与本机设置 | 增删行或排序就会整体错位 |
| 用 TCP 端口做调试通道 | 要分配端口、弹防火墙、多 worktree 冲突；命名管道没有这些问题 |

## 8. 术语

- **配方（recipe）**：清单里的一行，描述一个软件怎么从官网页面走到下载链接，以及下完怎么处理。全机器共享，进版本库。
- **本机设置（local settings）**：启用状态、下载目录、是否走代理、是否参加高频检查。只属于这台机器，不进版本库。
- **就绪 / settled**：页面被判定为"脚本已经装配完、可以点了"的状态，由页面自身的信号合成，不是固定等待。
- **判重**：在传输文件体之前判断远端文件与本地是否同一个版本。
- **只查不下（test / probe）**：走完整条链路直到能回答"有没有更新"，随即取消传输。
- **无人值守**：没有人看着的运行时段。常驻实例的后台轮次是常态，命令行 `--download-all --auto-close` 是一次性的那种。
- **常驻（resident）**：程序留在通知区域、自己按时间表跑的默认形态。关掉窗口只是收起来，不是退出。
- **全量 / 高频**：两套时间表。全量在配置的若干时刻跑所有启用项；高频按短间隔只跑勾了 `FrequentCheck` 的那几项。
- **门禁（gate）**：后台轮次开跑前的那组判断——有批次在跑 / 系统报告用户忙。两种轮次遇到都直接丢掉这一趟，不补跑。

## 9. 给 AI agent 的工作指引

**动手之前问自己四个问题：**

1. 我要改的东西属于**配方（共享）**还是**本机设置（私有）**？放错一边会污染所有用户的版本库，或让本机数据无处可存。
2. 这个改动会不会**写用户的配置文件**？会的话，外部已被修改时的行为是什么？失败时怎么恢复？
3. 这个改动会不会**改变判重结果**？会的话，"没更新就不动磁盘"还成立吗？
4. 这个改动会不会**改变页面就绪的判定**？会的话，先去 §7 确认它不是一个已经撤回过的想法。

**验证路径（按成本从低到高）：**

1. 纯逻辑改动 → 先用 xunit 覆盖（`.tab` 格式、设置合并、批量顺序与取消、旧版本清理判定都已有测试）。
2. 运行期行为 → Debug 构建启动，用本 worktree 的 Debug MCP 单项验证；页面时序问题先看页面就绪诊断，把"页面慢 / 定位不对 / 点了无效"分开，再动代码。
3. 性能类改动 → 必须报冷缓存下的数据，并且点名说明已知的慢站点有没有回退。
4. 代码、日志和调试接口都定位不了 → 才上调试器（用法与边界见 AGENTS.md）。

**容易误判的地方：**

- "这一项失败了" ≠ "配方错了"。先确认不是就绪判定、代理、或单实例冲突。
- "磁盘上没变化" 是**正确**结果，不是"什么都没干"。
- 表格里看到的转义形式（换行、制表符）就是存储形式，不要在显示层"顺手还原"。
- 改到共享库里的文件等于改 submodule，会影响其它应用。
